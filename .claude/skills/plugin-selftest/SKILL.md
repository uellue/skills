# Plugin self-test

The subject is always the kaizen plugin in this checkout. The scenario (`benchmarks/plugin-newcomer/scenarios/<name>.md`, with an optional project folder of the same name) is only the input the newcomer brings; when the run reaches one of the plugin's skills, including `kaizen:hallway-test`, that is a step to observe, never a test of the scenario's project. Do not invoke `kaizen:hallway-test` for this; this procedure is the hallway test of the plugin, and its results file stands in for the hallway record (`design/hallway/`).

Run every command from the repository root (`cd "$(git rev-parse --show-toplevel)"`).

0. **Eval suites first.** What one prompt decides (which skill starts, first-turn gates, what a skill writes) is checked by `claude plugin eval`, cheaper and repeatable; the newcomer run below is for what it cannot see, a conversation over many turns. Give the maintainer the commands from `plugins/kaizen/evals/README.md` ("Run"): the trigger table after any change to a skill's description, the comparison after a change to a tested skill. Expected effects of the change go into the README before the run. Afterwards read the results folder the command names, compare with the expected effects and the previous run, and record the outcome in the README and the ledger rows involved. Without a scenario argument and with only description changes, this step alone may be the self-test; ask.
1. **Scenario and model.** Take them from the arguments; without a scenario, list `benchmarks/plugin-newcomer/scenarios/*.md` with their first line and ask. Model: the argument, else Opus; run each scenario on Sonnet from time to time too, since a first user skims and a cheaper tester is closer to that (a colleague found the Opus tester "too smart, not lazy enough"). Name the commit under test and say whether the plugin has uncommitted changes.
2. **Prepare.** `python3 benchmarks/plugin-newcomer/brief.py <scenario>` creates the scratch project and prints the filled brief; the scratch directory is in its first line.
3. **Run.** Start one fresh general-purpose agent in the background, on the chosen model, with the printed brief (without the header line) as its whole prompt. Tell the maintainer the cost to expect: about 15 k output tokens and three minutes per run so far. While it runs, invite the maintainer once to note thoughts for the debrief. Answer its questions, if any, from the plugin's documents; what you cannot answer goes to the maintainer.
4. **Check.** For every claim the report makes about the plugin's text or scripts, check it yourself (a grep or a run each); a claim you cannot confirm is marked so.
5. **Grade.** By a fresh agent that changed none of the skills (Sonnet is enough), given only the report, the key and your checked claims, so that the grade does not lean on the main session's reasoning; when no grader can run, grade yourself and say "graded by the main session, not independent". Against `benchmarks/plugin-newcomer/key.md`: the items for all scenarios and those for this scenario, each held, partly, not held, not reached or not reported. Write `benchmarks/plugin-newcomer/results/<date>-<scenario>.md` (add `-2`, `-3` for further runs that day): commit, scenario, model, output tokens (`python3 plugins/kaizen/scripts/usage.py agent-<id>`), who graded, the table, the comparison with the previous run of the same scenario, the setup misfit the tester named.
6. **Hand over.** New findings go into `design/kaizen.md` as proposals with a lean each, not applied; a finding that the key lacks becomes a key item when the maintainer agrees. Summarise for the maintainer in a few lines: what held, what did not, what changed since the last run, the decisions waiting. Commit the result when the maintainer has asked for commits. When the run was the final acceptance test of a release, the order is push, merge, then the debrief in a fresh session; its proposals go into the next release.
