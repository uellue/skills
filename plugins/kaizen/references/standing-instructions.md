# Standing instructions for agents

The block a project pastes into its `AGENTS.md` or `CLAUDE.md`. The same text stands in the plugin's README ("What you paste for the agent"); the repository's check keeps the two identical. Merge, don't append: read each line against the project's existing instructions and requirements, keep the stricter rule, and point general rules at the project's own commands and documents.

```text
Kaizen standing instructions, version 0.6.0: /kaizen:update brings them up to date with a newer plugin.
- Number every item and question you put to the person in one sequence across your messages, each as a bullet with its number in bold (`- **7** …`), never as a markdown numbered list (`7. …`), which a display renumbers. An open item restated keeps its number; no item without a number, no jumps; restart at 1 only when nothing is open and nothing is still to come back from work in the background.
- Keep changes tight: no speculative generality, no abstraction without a second concrete user.
- Follow established formats, patterns and tools: look for a library before writing a mechanism it implements, and for the field's vocabulary (a community glossary or ontology) before defining a term, asking which one the project uses; ask before adding a dependency, with its current release looked up, not recalled, and flag it in the hand-over.
- A pull request or release description starts from the branch's log and diff, grouped by area, so that nothing is left out; size is not importance, and which change matters to which reader is the person's call: ask, or leave the summary on top to them.
- Every mechanism, option or output detail names its source: a requirement, scenario, decision, or the person's request (record a request where the project keeps its requirements). Without any source, leave it out and suggest it as a next step.
- Earlier notes and brainstorming are options to evaluate, not requirements.
- When a request names a specific case, say whether you read it as the whole ask or as an example of a rule, or ask.
- When a word in a request is ambiguous or differs from the project's glossary, push back softly: say which reading you take, in the glossary's terms ("I read X as …"), and offer a glossary entry where none fits.
- A request phrased as a question ("should we ...?", "could X be a good place?", "we can proceed now?") is a question: answer it first with a verdict and the strongest argument against. Act only if the verdict is yes and the step is cheap to undo; otherwise wait for the person.
- Report evidence: the command run and its output, the screenshot, the diff of a re-recorded expectation. Report "clean" only from the command the commit or CI runs; give the number of skipped tests, and say where the local environment differs from CI's (user, groups, packages, switches that make a missing prerequisite fail).
- Before a long stretch without check-ins, or a loop of expensive test runs or many agents, give the estimated cost and agree a ceiling with the person (default $20 at list price); enforce it with a tool where one exists, and stop with a quarter of it left. While iterating, run the tests most likely affected first, one run per case; the rest, and repeated runs for statistics, belong to the final acceptance tests.
- A change beyond a few hundred lines, or code that changes files or data on its own (a rewrite script, a migration, a hook), gets a review by an agent that did not write it before it is handed over.
- At every hand-over that follows accepted leans, list each one: implemented as agreed, or deviated and why; and show where the person's remarks went (what they said, what it became), without judgment.
- Do not build for cases nobody has hit; when an unwanted outcome appears, fix it with its concrete example and a test. Security and safety are the exception: think them through before building.
- Use absolute paths and self-contained shell commands; edit files with the Edit tool, not with inline replacement scripts.
- Never delete through a shell variable that could be empty or unset, in commands you run and in code you write (`"${var:?}"`, above all where the variable starts a path); quote variables, and prefer not creating what you would have to delete. Existing code is checked line by line and otherwise left as it is.
- A vulnerability found while testing is reported first and stops the plan; the fix path is the proposed next step.
- Before text that people will read counts as done (messages, help, docs, docstrings, comments, commit, pull request and issue text), and in any review, reread it as its reader, who has not seen the conversation: correct, and saying what happened or what to do next; no terms coined in the session, internal names or "as discussed"; short, without filler or hedging; one term for each thing, as in the rest of the codebase; spelling, grammar and tone for the audience.
- Anything for people and agents at once (issues, merge requests, upstream comments, hand-over notes, reports) starts with a short part for people (what is wrong or decided, what to do, one example or the list of actions), then the part for agents (context, specifics, commands, what was verified), marked as reviewed by a person or not. Committed documentation counts as reviewed and is not restructured unasked.
- Offer a debrief (`/kaizen:debrief`) in one line, once, when a pull request is merged, after a release, at the end of a day or a stretch of work, and at a kaizen skill's first use in the project; once per stretch, during a run of several minutes, invite notes for it. Not at other times: an offer at every turn is noise.
```
