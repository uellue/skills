# Hallway test

Text id `033d150d`: first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py hallway-test 033d150d` as it stands and pass on what it prints, if anything (it is silent when all is well; if it fails, carry on).

Use plain words with the person: explain a term of this plugin the first time you use it with them, as `${CLAUDE_PLUGIN_ROOT}/references/words.md` does.

The name comes from grabbing a person in the hallway and watching them use the product. Here the person is a sub-agent that has not seen the implementation, the specs or the conversation that produced the code, so it cannot un-know what the author knows. It reads the requirements and the user-facing documentation, decides what should happen, tries it, and reports where reality differs. It regularly finds defects that the test suite has enshrined and that every scenario missed.

The test is the third moment for a persona and a process that the `walkthrough` skill imagined before the thing existed: the tester executes the same walk with fresh eyes, and the comparison of imagined and observed is the validation of the specification. Take the persona from the project's stakeholder record (`design/stakeholders.md`) and the coverage from the walk-through's steps and acceptance examples when they exist.

Modes, often combined:

- **Behaviour**: the tester builds test inputs, writes its expectation for each before running, runs the tool, compares, classifies.
- **By eye**: for output meant for people, the tester drives the tool in a real terminal and judges screenshots, which catches what text parsing never sees: output scrolled off, noise drowning the signal, lines wrapping, a pager hiding diagnostics. The bundled driver `${CLAUDE_PLUGIN_ROOT}/scripts/xterm-shots.py` starts an xterm under a virtual X server, sends keys and takes screenshots; it needs `xvfb`, `xterm`, `xdotool` and `imagemagick` (ImageMagick's `import`) installed, which a devcontainer or VM can carry. A rendered web page cannot be judged by eye yet (planned); for now a page is judged by its source and its text, and the record says so.
- **Diagnosis**: the process under test is finding out what is wrong. The main session injects faults that look real into a running system; the tester gets the symptom, the persona and the user-facing documents only, and its investigation log, verdict, time and tokens are the measurement. Brief in `${CLAUDE_PLUGIN_ROOT}/references/diagnosis-brief.md`.
- **Hint-following (the impatient user)**: a first user who does not read. They skim the README for a command that looks like what they want, run it, and then follow only what the program prints, the way a good compiler or git leads you on. The tester sees the README only through `${CLAUDE_PLUGIN_ROOT}/scripts/skim.py` (headings, command blocks and bullets that carry a command), because an agent told to be lazy still reads everything it is given: the laziness is enforced by what it can see. Every time the output gives no next step and the tester has to go back to the documents, the chain breaks; each break is a finding whose fix belongs in the program's output, with the text it should have printed. Measured: commands to the goal, breaks, minutes. Check the transcript afterwards: a `Read` of a documentation file that the brief did not allow invalidates the run. Brief in `${CLAUDE_PLUGIN_ROOT}/references/impatient-brief.md`. The other modes test whether the tool does the right thing; this one tests whether a person who reads nothing gets there.
- **Documents and instruction files**: the subject is a README, a guide or an agent instruction file (`AGENTS.md`, `CLAUDE.md`). For a README, the tester follows it from a clean checkout and reports where it stops. For an instruction file, the test is an evaluation: variants of the file in separate worktrees × typical tasks × one fresh, cheap agent per cell, an answer key written before the runs, a blind grader that did not write the variants, and the usage per cell; it decides layout questions by measurement instead of argument.

A borrowed checklist, with thanks: the eleven CLI usability criteria of the MIT-licensed cli-ux-tester skill by ali5ter, in `${CLAUDE_PLUGIN_ROOT}/references/cli-ux-checklist.md`, as an extra pass for command-line tools.

## Before launching

A request to "test" something can mean its own tests or a first user trying it: before anything else, say which reading you take ("I read 'test' as a first user trying it, not automated tests") and let the person correct it.

Settle these with the user in one message: first the questions only the person can answer, then the rest with your lean for each, so that one "yes" accepts them; they become the tester's brief. For an existing tool before its first hand-over, keep that message short: the reading of the request, the no-requirements line, the questions only the person can answer (who is first, how a wrong result would show, who answers during the run, where the record goes), then everything else as one block of leans. When the subject is a framework, a plugin or a process, the persona brings a sample project of their own: it is input, not the subject, and the brief names both.

1. **The persona**, from the stakeholder record; offer to add one if the first user of this thing is not in it. With no record and no wish to start one, ask one question (who uses it first, what do they already know?) and mark the persona "not on record" in the brief; when the person cannot say, the tester plays a colleague who has only the README, marked in the brief as assumed by you; never a default of your own.
2. **What the tester may read.** Only what a first user would have: the requirements, the user documentation, the command's help, sample data they would have (copied, as in item 3). Name the files or directories; forbid the rest explicitly (source, tests, specs, design notes, git history). The point of the test is the fresh view; every extra document weakens it. If nothing is built yet, stop and hand over to `/kaizen:playbook`, which decides between discovery and the requirements interview. If something is built but no requirements exist, say so: for a tool that works for its author, the playbook's path is this test now, with the person as the source of the persona, and the requirements reconstructed afterwards from its findings. Go ahead if the person wants: a tester that has to invent the requirement tests its own invention, so the brief says so.
3. **The tool and how to run it.** The command line or entry point, where test inputs may be created (a scratch directory, never the repository), what may be installed, what must not be touched (a read-only data mount is read-only). A tool that acts on something real it could damage (what counts is listed in the decision record's safety row) is tested only against a stand-in or in a dry run unless its owner agrees otherwise, under the rules of the decision record's safety row (`${CLAUDE_PLUGIN_ROOT}/references/decision-record.md`); without a record, those rules apply as written there. Unless the code or the repository already answers it (a tool that only reads and prints; data kept in git), ask before you or the tester run the tool on data whether the data are the originals and whether another copy exists; if this is the only copy, propose a backup before anything else. Data the tester needs is copied into the scratch directory by you, with links resolved (`cp -rL`) and no absolute paths left pointing at the original; where possible the original stays read-only for the tester. The tester runs from scratch and is not given the original's path. For a tool that touches shared host state (virtual machines, services, keys), each tester gets a project name of its own, and `HOME` is not redirected for a tool that uses ssh (ssh reads `~` from the account, not from `HOME`); where a redirect is unavoidable, name it in the record as a distortion.
4. **How a wrong result would show**, for a tool that computes results: ask how the person would notice a wrong result, which inputs are hard (overlapping, noisy, edge cases), and for an input with a known answer; without one, the tester builds inputs with known values, hard ones among them.
5. **The coverage to insist on.** The acceptance examples by ID from `design/examples.md`, the walk-through's steps, the requirements' use scenarios (and, with OpenSpec, its scenarios), the last test's gaps, plus "add experiments of your own". Each mandatory case names the example ID it serves, so that the tester asserts the outcome the user cares about and not the mechanism the author expects. Tell the tester to spend at least half its effort outside the list: the worst defects tend to lie outside every planned case. When the person cannot name any coverage, offer a short walk-through of the first user's first steps (`/kaizen:walkthrough`) to find it. Before a first hand-over, say where the tool writes on its users' own data (from the code, or ask) and whether that is acceptable; the answer is a mandatory case. For by-eye tests: the screens to reach, the terminal size, the keys to press.
6. **Who answers questions.** The tester asks the main session when the requirements do not say what should happen; the main session answers from the design and records what it could not answer confidently as TODO items for the principal. With no design, the principal answers: ask whether they stay available during the run, or collect the questions for afterwards.
7. **Where the record goes** and the summary length. With no `design/` yet, ask before creating it and whether committed files become public, as in the playbook's step 3.
8. **The mode** (above), with your lean: behaviour for "does it do what it should", hint-following for "will people who don't read get there", by eye for output meant for people.
9. **The model, the expected cost and the duration**, stated before launching; wait for an explicit yes (a repeated or empty command is not one). Measured so far: about 10 k to 15 k output tokens and two to three minutes for a short tester run reading a README and a few files (Opus); about 46 k output tokens and 14 minutes for a behaviour test of a small CLI (Sonnet). Anything else is a guess and is called one.

## The brief

Spawn a general-purpose sub-agent in the background with a brief built from the template in `${CLAUDE_PLUGIN_ROOT}/references/tester-brief.md`: the persona, the strict reading rules, the command reference as a user would get it, the method (create, write the expectation down first, run, compare, classify as matches / bug / surprising but defensible / gap / question), the mandatory coverage, the instruction to ask, and the report structure. For by-eye tests, use `${CLAUDE_PLUGIN_ROOT}/references/visual-brief.md`, which describes the driver and insists that the tester judges only screenshots; for diagnosis, `${CLAUDE_PLUGIN_ROOT}/references/diagnosis-brief.md`; for hint-following, `${CLAUDE_PLUGIN_ROOT}/references/impatient-brief.md`.

Two mechanics that the first uses taught:

- **Expectations are a file, written first.** The tester writes `expectations.md` in its scratch directory before its first run and reports its timestamp; the main session checks the order. A transcript with no expectation text and the first command in the first minute means the comparison is worthless.
- **The report comes back as the tester's final message.** Harness rules may forbid a sub-agent from writing report files; the main session writes the record from the message, with the screenshot file names, so that nothing is lost when the tester cannot write.

Model: a cheaper model is enough for the by-eye tester, which looks and reports, and for the eval cells of an instruction-file test; the behaviour and diagnosis testers benefit from the session's model, since they reason about what should happen.

## While it runs

Answer the tester's questions from the design, with the reasoning, and tell it when a question exposed a bug (then fix the bug in the normal way, with its test, and tell the tester the tool has changed). Keep a running list of what you could not answer with confidence; those go to the principal as decisions, not as your guesses.

## After

1. Read the report. Verify each bug claim against the code before accepting it; a tester with no source access describes symptoms, and the cause may differ. Get its cost and its duration from `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/usage.py agent-<its id>`, not from the tester's own estimate (testers have been wrong by a factor of three).
2. Write the record to `design/hallway/<date>.md`: what held up, what was fixed with its test (and, with OpenSpec, its scenario), the answers given, a TODO list for the principal with your lean per item, and for every defect "what would have caught this". Propose committing it on the working branch of the repository that holds the records (a new branch if that repository is on its main branch; commit it if the person has asked you to commit): it becomes a source that requirements and specs cite, and a record that stays uncommitted can be lost while documents still cite it. The tester's long report is for agents; the human part is the summary at the top.
3. For every defect, add what would have caught it: a test, a rule, a check. A defect without that answer is only half fixed.
4. When the principal has decided the leans, the hand-over lists each accepted lean: implemented as agreed, or deviated and why.
5. Keep the experiment reproducible: the brief, the answer key or expectations, the answers given, the usage, and a small script that re-runs any experiment, saved together next to the record or in a named directory, with relative paths. This applies to every measurement, not only to hallway tests; an instruction-file eval whose prompts were not saved cannot be repeated.
6. If a walk-through preceded the test, add the comparison to it: per step, imagined versus observed.
7. With OpenSpec, the test runs after apply and before archive (the playbook's hand-off).
8. If no requirements existed, offer to reconstruct them now from this record and the tool (`/kaizen:requirements`, from the record), as the playbook's path for an existing tool promises.

## Rules

- The tester never modifies the repository, never reads what it was forbidden, and says in the report what it was given, including anything the harness attached that it did not ask for.
- Expectations are written before running, or the comparison means nothing.
- A finding is a moment: the exact command, what was expected, what was observed, the relevant stderr lines or the screenshot file name.
- Do not fix during the test what the tester reported as a question; decide first whether it is a bug or a design choice, then fix with its test.
- A finding that is a vulnerability (data readable by the wrong user, a credential exposed, an unsafe default) is reported to the user first and the plan stops there; the fix path is the proposed next step, not an item further down the list.
- If there is no ledger yet, or it shows no debrief, mention the debrief in one line (`/kaizen:debrief`, after a stretch of work).
- At the end, one line into the project's ledger: what in this skill did not fit. If the file is new, announce it first (playbook, Rules).
