# Hallway test

Text id `bb4cc78b`: first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py hallway-test bb4cc78b` as it stands and pass on what it prints, if anything (it is silent when all is well; if it fails, carry on).

A fresh sub-agent that has not seen the implementation, the specs or the conversation tries the thing as a first user would, with only the requirements and the user documentation, and reports where reality differs from what they promise. Its persona comes from the stakeholder record (`design/stakeholders.md`), its coverage from the walk-through's steps and the acceptance examples when they exist; comparing what the walk imagined with what the tester saw validates the specification.

Use plain words with the person: explain a term of this plugin the first time you use it with them, as `${CLAUDE_PLUGIN_ROOT}/references/words.md` does; keep a message to about fifteen lines, one step or question at a time; number a message's items from 1 in one sequence that never restarts within it, so the person can answer by number.

Modes, often combined:

- **Behaviour**: the tester builds test inputs, writes its expectation for each before running, runs the tool, compares, classifies. Brief: `${CLAUDE_PLUGIN_ROOT}/references/tester-brief.md`; for a command-line tool, add the eleven-point checklist in `${CLAUDE_PLUGIN_ROOT}/references/cli-ux-checklist.md` as an extra pass.
- **By eye**: for output meant for people, the tester drives the tool in a real terminal through `${CLAUDE_PLUGIN_ROOT}/scripts/xterm-shots.py` (needs `xvfb`, `xterm`, `xdotool` and `imagemagick`) and judges screenshots only, which catches what text parsing never sees: output scrolled off, lines wrapping, a pager hiding diagnostics. A rendered web page cannot be judged by eye yet (planned): it is judged by its source and its text, the person looks at it in the local preview with the examples as a checklist, and the record says so. Brief: `${CLAUDE_PLUGIN_ROOT}/references/visual-brief.md`.
- **Diagnosis**: the process under test is finding out what is wrong. The main session injects faults that look real into a running system; the tester gets the symptom, the persona and the user-facing documents only, and its investigation log, verdict, time and tokens are the measurement. Brief: `${CLAUDE_PLUGIN_ROOT}/references/diagnosis-brief.md`.
- **Hint-following (the impatient user)**: a first user who does not read: they skim the README for a command that looks right, run it, and then follow only what the program prints. The tester sees the README only through `${CLAUDE_PLUGIN_ROOT}/scripts/skim.py`, so its laziness is enforced; each time the output gives no next step, the chain breaks, a finding whose fix belongs in the program's output. Measured: commands to the goal, breaks, minutes; a `Read` of a document the brief did not allow invalidates the run. Brief: `${CLAUDE_PLUGIN_ROOT}/references/impatient-brief.md`.
- **Documents and instruction files**: for a README, the tester follows it from a clean checkout and reports where it stops. For an agent instruction file (`AGENTS.md`, `CLAUDE.md`), an evaluation: variants of the file in separate worktrees × typical tasks × one fresh, cheap agent per cell, an answer key written before the runs, a blind grader that did not write the variants, the usage per cell; layout questions are decided by measurement, not argument.

## Before launching

When the request says "test", which can mean its own tests or a first user trying it, say before anything else which reading you take, in one line that also says what the test is ("I read 'test' as a fresh agent trying it as a first user and reporting what breaks, a hallway test; not automated tests"), and let the person correct it.

Settle the items below in short messages, each numbered from 1: first the questions only the person can answer (with, for a tool that writes, whether the data are the originals and another copy exists, item 3); then, with the answers in hand, your leans as one block that one "yes" accepts (when it would run past fifteen lines, the record's place and the ledger get a message of their own); last, on its own, the model, cost and duration with the request to start (item 9). Together they become the tester's brief. For an existing tool before its first hand-over, the first message is the reading of the request and the no-requirements line, one line each, and the questions only the person can answer (who is first, how a wrong result would show, which cases matter most, who answers during the run, where the record goes); whether to start a stakeholder record goes into the leans. When the subject is a framework, a plugin or a process, the persona brings a sample project of their own: it is input, not the subject, and the brief names both.

1. **The persona**, from the stakeholder record; offer to add one if the first user of this thing is not in it. With no record, ask one question (who uses it first, what do they already know?), offer to start the record among the leans (one entry: role, goal, knowledge, environment, what they never read, and who described them; the fields not asked marked unknown), and mark the persona "not on record" in the brief; when the person cannot say, the tester plays a colleague who has only the README, marked in the brief as assumed by you; never a default of your own.
2. **What the tester may read.** Only what a first user would have: the requirements (on the small path, the examples and the decision record's need note), the user documentation, the command's help, sample data they would have (copied, as in item 3). Name the files or directories; forbid the rest explicitly (source, tests, specs, design notes, git history); a one-file tool is both the command and its source, so the tester gets a copy to run in scratch and is told not to open it. Every extra document weakens the fresh view, and what you yourself notice in the code stays out of the brief, kept for the record's comparison. If nothing is built yet, stop and hand over to `/kaizen:playbook`, which decides between discovery and the requirements interview. If something is built but no requirements exist, say so: for a tool that works for its author, the playbook's path is this test now, with the person as the source of the persona, and the requirements reconstructed afterwards from its findings; go ahead if the person wants, and the brief says that a tester that has to invent the requirement tests its own invention.
3. **The tool and how to run it.** The command line or entry point, where test inputs may be created (a scratch directory, never the repository), what may be installed, what must not be touched (a read-only data mount is read-only). A tool that only reads and prints needs none of the rest of this item.
   - A tool that acts on something real it could damage is tested only against a stand-in or in a dry run unless its owner agrees otherwise, under the decision record's safety row (`${CLAUDE_PLUGIN_ROOT}/references/decision-record.md`), which also lists what counts; without a record, those rules apply as written there.
   - Unless the code or the repository already answers it (data in git with a remote), ask before you or the tester run the tool on data whether the data are the originals and whether another copy exists; if this is the only copy, make a copy first, outside the project and announced with its path, and run nothing on the data until it exists.
   - Data the tester needs is copied into the scratch directory by you, with links resolved (`cp -rL`) and no absolute paths left pointing at the original; where possible the original stays read-only for the tester; the tester runs from scratch and is not given the original's path.
   - For a tool that touches shared host state (virtual machines, services, keys), the person agrees first that testers may touch it, each tester gets a project name of its own, and `HOME` is not redirected for a tool that uses ssh (ssh reads `~` from the account, not from `HOME`); where a redirect is unavoidable, name it in the record as a distortion.
4. **How a wrong result would show**, for a tool that computes results: ask how the person would notice a wrong result, which inputs are hard (overlapping, noisy, edge cases), and for an input with a known answer; without one, the tester builds inputs with known values, hard ones among them.
5. **The coverage to insist on.** The acceptance examples by ID from `design/examples.md`, the walk-through's steps, the requirements' use scenarios (and, with OpenSpec, its scenarios), the last test's gaps, plus "add experiments of your own". Each mandatory case names the example ID it serves, so that the tester asserts the outcome the user cares about, not the mechanism the author expects; at least half its effort goes outside the list, where the worst defects lie. When the person cannot name any coverage, offer a short walk-through of the first user's first steps (`/kaizen:walkthrough`). Before a first hand-over, say where the tool writes on its users' own data (from the code, or ask) and whether that is acceptable; the answer is a mandatory case. For by-eye tests: the screens to reach, the terminal size, the keys to press.
6. **Who answers questions.** The tester asks the main session when the requirements do not say what should happen; the main session answers from the design and records what it could not answer confidently as TODO items for the principal. With no design, the principal answers: ask whether they stay available during the run, or collect the questions for afterwards.
7. **Where the record goes** and the summary length; the record and the files written before it go on a working branch, a new one if the repository is on its main branch. With no `design/` yet and the playbook not yet run, ask before creating it, and whether committed files become public (then it goes where the playbook's step 3 says).
8. **The mode** (above), with your lean: behaviour for "does it do what it should", hint-following for "will people who don't read get there", by eye for output meant for people.
9. **The model, the expected cost and the duration**, stated before launching; wait for an explicit yes (a repeated or empty command is not one). Measured: about 10 k to 15 k output tokens and two to three minutes for a short README run (Opus); about 46 k and 14 minutes for a behaviour test of a small CLI (Sonnet); anything else is a guess and is called one. A cheaper model is enough for the by-eye tester and the eval cells; the behaviour and diagnosis testers benefit from the session's model.

## The run

Spawn a general-purpose sub-agent in the background with the mode's brief filled in: the persona, the strict reading rules, the command reference as a user would get it, the method (create, write the expectation down first, run, compare, classify as matches / bug / surprising but defensible / gap / question), the mandatory coverage, the instruction to ask, and the report structure. Two mechanics:

- **Expectations are a file, written first.** The tester writes `expectations.md` in its scratch directory before its first run and reports its timestamp; the main session checks the order. A transcript with no expectation text and the first command in the first minute means the comparison is worthless.
- **The report comes back as the tester's final message.** Harness rules may forbid a sub-agent from writing report files; the main session writes the record from the message, with the screenshot file names.

While it runs, answer the tester's questions from the design, with the reasoning, and tell it when a question exposed a bug (then fix the bug in the normal way, with its test, and tell the tester the tool has changed). Keep a running list of what you could not answer with confidence; those go to the principal as decisions, not as your guesses.

## After

1. Read the report. Verify each bug claim against the code before accepting it; a tester with no source access describes symptoms, and the cause may differ. Get its cost and its duration from `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/usage.py agent-<its id>`, not from the tester's own estimate.
2. Write the record to `design/hallway/<date>.md`: what held up, what was fixed with its test (and, with OpenSpec, its scenario), the answers given, a TODO list for the principal with your lean per item, and for every defect "what would have caught this" (a test, a rule, a check; a defect without that answer is only half fixed). The tester's long report is for agents; the human part is the summary at the top. Propose committing it on the working branch of the repository that holds the records (commit it if the person has asked you to commit): a record that stays uncommitted can be lost while documents still cite it.
3. When the principal has decided the leans, the hand-over lists each accepted lean: implemented as agreed, or deviated and why.
4. Keep the experiment reproducible: the brief, the answer key or expectations, the answers given, the usage, and a small script that re-runs any experiment, saved next to the record with relative paths. This applies to every measurement.
5. If a walk-through preceded the test, add the comparison to it: per step, imagined versus observed.
6. With OpenSpec, the test runs after apply and before archive.
7. If no requirements existed, offer to reconstruct them now from this record and the tool (`/kaizen:requirements`, from the record), as the playbook's path for an existing tool promises.

## Rules

- The tester never modifies the repository, never reads what it was forbidden, and says in the report what it was given, including anything the harness attached that it did not ask for.
- Expectations are written before running, or the comparison means nothing.
- A finding is a moment: the exact command, what was expected, what was observed, the relevant stderr lines or the screenshot file name.
- Do not fix during the test what the tester reported as a question; decide first whether it is a bug or a design choice, then fix with its test.
- A finding that is a vulnerability (data readable by the wrong user, a credential exposed, an unsafe default) is reported to the user first and the plan stops there; the fix path is the proposed next step.
- Offer the debrief in one line (`/kaizen:debrief`) when the test ends a stretch of work (before a merge or a release), was this skill's first use in the project, or the ledger shows no debrief yet.
- At the end, one line into the project's ledger: what in this skill did not fit. If the file is new, say where it goes and whether it is committed, and start it from `${CLAUDE_PLUGIN_ROOT}/references/ledger.md`.
