# Sync

Text id `2713e2f0`: first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py sync 2713e2f0` as it stands and pass on what it prints, if anything (it is silent when all is well; if it fails, carry on).

The project's backlog lives upstream (its issue tracker and pull requests); the ledger holds how the work is done, and its notes section is the inbox for ideas dropped during work until they find their place. A sync moves things across that border in both directions, with `git` and the tracker's CLI (`gh` for GitHub, `glab` for GitLab), the person supported rather than replaced: reading is the agent's to do; anything that changes something (a rebase, a push, a post) is proposed with its command and explained where it may be unfamiliar, and the agent runs it only where the person has authorised that, otherwise the person runs it. Nothing leaves the machine without the person's yes.

Use plain words with the person: explain a term of this plugin the first time you use it with them, as `${CLAUDE_PLUGIN_ROOT}/references/words.md` does; keep a message to about fifteen lines, one step or question at a time; number items in one sequence across messages, never restarting while any is open, so the person can answer by number.

## Steps

1. **The setting.** Read the "Issue tracker" section of the project's instruction file (`CLAUDE.md` or `AGENTS.md`): where issues live, when to read them, how often to post, whose yes counts, and who runs commands that change something (a push, a rebase, a post: the person, or the agent after a yes). Without one, or where a point is missing, ask those questions once and offer to record the answers there (`${CLAUDE_PLUGIN_ROOT}/references/changelog.md`, 0.6.0, has the section to fill in); a project with no tracker syncs only its repository.
2. **In.** `git fetch` and say what moved: the default branch, the branches of open pull requests, the current branch against its upstream, or against the default branch when it was never pushed (behind, ahead, diverged; a rebase or merge is offered with its commands, never done unasked). From the tracker: issues and pull requests opened, closed or merged since the last sync (the ledger's notes say when that was; a first sync starts from the update's first look). For each ledger row or note that a closed issue or merged pull request settles (not one that merely mentions it), propose the status ("done in pull request 9"); for each open question in the project's records that cites a closed issue, whenever it closed, say whether it is stale; name issues and pull requests from others that have waited more than two days for an answer as places where the person's answer is needed, each with what it asks of them in one line (no draft reply: the person follows up with people themselves, unless they ask for one). This may take two messages.
3. **The inbox.** For each note in the ledger's notes section ("Notes for the next debrief", the inbox) that is not yet routed, propose one destination, numbered: a new issue (its title; the body drafted once the person picks it), a comment on an existing one (which, and what it would say; on an issue someone else opened only when the person asks, since they answer people themselves), a ledger row (a proposal about how the work is done), already there (an existing row or line: name it), or dropped. Notes that belong to the debrief (how the session went) stay for it. One yes may take the list.
4. **Out.** List what waits to go upstream: unpushed commits and branches (what each holds, not only its name), drafts the person asked for, the issues and comments picked in step 3; and, apart, where the person's answer is needed (step 2). Each item says what it is about and what the person would decide, in words they know without the earlier messages. Before the first draft, check that git ignores the folder (`git check-ignore -q .claude/drafts/x`) and otherwise offer the line `/.claude/drafts/` for `.git/info/exclude` (or `.gitignore`), as for `.claude/debriefs/`. Each draft is split into a part for people and a part for agents; on a public tracker, ask whether the agents' part goes out too. On the person's yes, and where they authorised the agent to post, post it with the tracker's CLI and show the link; otherwise give the person the command or the text and the place, and help them through it. A commit that fixes an issue says `Closes #n`, a part of one `Refs #n`.
5. **Record.** In the ledger: each routed note keeps only its link ("→ #18", "→ row 12", "dropped"), or, until a draft is posted, "→ draft `.claude/drafts/<file>`", which the next sync replaces with the number; statuses from step 2; one line in the notes with the date of this sync, so the next one knows where to start. Commit on the current working branch with the person's agreement, and say so when that branch also carries unpushed work of another kind.

## Rules

- Never post, push, close, label, rebase or force anything without the person's yes for that item; reading is free.
- Issues stay in the tracker: never copy an issue's text into the ledger; link it and say in one line what it is about.
- Say which layer each finding is about: the project's work (the tracker) or the work with the agent (the ledger).
- Ideas dropped on the way and offers left open go into the inbox at once (`${CLAUDE_PLUGIN_ROOT}/references/ledger.md`).
- At the end, one line into the project's ledger: what in this skill did not fit. If the file is new, announce it first (playbook, Rules).
