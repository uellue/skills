# Field test

Text id `4d4d52df`: first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py field-test 4d4d52df` as it stands and pass on what it prints, if anything (it is silent when all is well; if it fails, carry on).

A field test puts the subject in front of a real person in a real setting: the person works, the agent follows along through channels both agreed and checked, and they talk about what happens while it happens. It finds what simulations, unit tests and agent-only hallway tests cannot: the real data, the real machine, the person's own way of working. Every setting is different, so most of the work is fitting the test to it with the person; this skill carries only what is general.

Use plain words with the person: explain a term of this plugin the first time you use it with them, as `${CLAUDE_PLUGIN_ROOT}/references/words.md` does; keep a message to about fifteen lines, one step or question at a time; number items in one sequence across messages, never restarting while any is open, so the person can answer by number.

## Steps

1. **The frame.** Read the project's records first (instruction file, requirements, stakeholder record, earlier field tests in `design/field-tests/`). Say in one line what a field test is and how it differs from a hallway test. Then ask, numbered, what the records do not answer: what exactly is under test; who takes part (the person, a colleague, users; people who have the role naturally rather than someone playing it); where it runs; what the person wants to learn; one shot on real work (instruments around a normal session, nothing reset, the work kept) or repeated from a fixed state (copies and a reset, its own runbook). Assume neither. Read the layers back and have them confirmed: where the person types, where the agent runs, where the subject runs, who else is involved. Change nothing and give no commands before the frame stands. When the subject will run outside an isolated VM, ask for the safety limits (step 3) in this first round, beside the frame.
2. **Fit it to the setting.** Walk the run through in the participant's shoes with the walk-through skill, at a depth that fits: for one shot on real work, its small path (the steps table); for a repeated test or other participants, the full walk. Settle open points with the requirements skill on one topic. The scenario's specifics come from this walk with the person, not from earlier tests.
3. **Safety.** When the subject runs outside an isolated VM or container (a shared machine, production, anything holding others' data or jobs), write down with the person, before any runbook: what it may read, write and start; how a run is stopped; what must never happen; who owns the machine and who agreed. They head the runbook (the decision record's safety row, `${CLAUDE_PLUGIN_ROOT}/references/decision-record.md`). Propose no command for that machine before; afterwards the agent only reads there until the person allows commands, one at a time. Recordings and exports can catch secrets: say what to look through before anything is shared.
4. **Channels.** Agree how data travels between the person, the agent and the subject: a view of the person's terminal (`${CLAUDE_PLUGIN_ROOT}/scripts/record.sh` records output and timing as it goes, never keystrokes, into the folder `FIELD_TEST_DIR` names, which must be one the agent can read), log files, forwarded ports, shared folders, the project's tracker. Check each from where the agent runs with a harmless probe (read a test line from the recording, one request to the port, a listing of the folder) and show the result, before the run starts.
5. **The runbook.** Write it to `design/field-tests/<scenario>-runbook.md` in the project (tracked): the variables first, then one command per line, each with what it does; small helpers only, readable at a glance. Read and adjust each step with the person; never hand over a script as "run this". Multi-line pastes break in some terminals: one line at a time. A brief for a participant follows `${CLAUDE_PLUGIN_ROOT}/references/field-test-brief.md`; when the person is the participant, it is a few lines in the runbook.
6. **The run.** The person works as they normally would and notes things as `#` lines at the prompt, in the notes file, or as "note for the debrief". The agent looks at the live view at each runbook step and when asked, not on a timer. It speaks up unasked in three strengths: a deviation it adapts to, mentioned inline ("you ran it twice, so I'll compare both"); a deviation that may compromise the test, said plainly with what it costs; something unsafe, said at once and loudly. The person can always override; the agent never gatekeeps beyond Claude's built-in safety checks.
7. **Evidence.** The person ends the recording; each session of the run is exported (`${CLAUDE_PLUGIN_ROOT}/scripts/transcript.py export <id>`); the run's evidence stays private in `.claude/field-tests/run-<n>/` (check that git ignores it; `record.sh --pack` makes one archive); the person looks through it for anything private before anything leaves.
8. **Process, then act.** Grade the run with one fresh reader agent and `${CLAUDE_PLUGIN_ROOT}/references/field-test-grade.md`, filled in, against the project's requirements; `transcript.py messages <id>` measures the replies' numbering and length. File each finding by its layer, with the person's yes: the subject's in the project's tracker (as its tracker setting says); the plugin's as a drafted issue for github.com/uellue/skills for the person to send; the method's in `design/field-tests/`. When the person corrects a grade, add the case to `design/field-tests/works-as-designed.md`. Offer the next run only after the findings were acted on, unless the person wants repeats from the same state to sample variation.

## Rules

- The person decides and works; the agent proposes, probes, watches and files.
- Say which layer each finding is about.
- Nothing of the evidence leaves the machine without the person's look and yes.
- At the end, one line into the project's ledger: what in this skill did not fit. If the file is new, announce it first (playbook, Rules).
