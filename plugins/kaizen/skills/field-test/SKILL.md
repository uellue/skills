Use it whenever the user wants to try out what they are working on in real use, take something from simulation or tests to a first real run, reproduce or fix an issue that appeared in real-world use with the session watching, have a colleague or user try it, or instrument a session to look at it together. Rather than the hallway test, which uses agents only, or a walk-through on paper.

# Field test

Text id `36c04a96`: first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py field-test 36c04a96` as it stands and pass on what it prints, if anything (it is silent when all is well; if it fails, carry on).

A field test puts the subject in front of a real person in a real setting: the person works, the agent follows along through channels both agreed and checked, and they talk about what happens while it happens. It finds what simulations, unit tests and agent-only hallway tests cannot: the real data, the real machine, the person's own way of working. Every setting is different, so most of the work is fitting the test to it with the person; this skill carries only what is general.

Use plain words with the person: explain a term of this plugin the first time you use it with them, as `${CLAUDE_PLUGIN_ROOT}/references/words.md` does; keep a message to about fifteen lines, one step or question at a time; number items as bold labels (`- **7**`, never `7.`), one sequence across messages, never restarting while any is open.

## Steps

1. **The frame.** Read the project's records first (instruction file, requirements, stakeholder record, earlier field tests in `design/field-tests/`). Say in one line what a field test is and how it differs from a hallway test. Then ask, numbered, what the records do not answer: what exactly is under test; who takes part (the person, a colleague, users; people who have the role naturally rather than someone playing it); where it runs; what the person wants to learn; and, asked in these plain words, not as a label: "Do you want to try it once, as part of your real work, keeping everything it produces? Or to run it several times from the same starting point, with everything reset in between?" (the first needs only the recording and notes around a normal session; the second copies and a reset, with its own runbook). Assume neither. Read the layers back and have them confirmed: where the person types, where the agent runs, where the subject runs, who else is involved. Change nothing and give no commands before the frame stands. When the subject will run outside an isolated VM, ask for the safety limits (step 3) in this first round, beside the frame.
2. **Fit it to the setting.** Walk the run through in the participant's shoes with the walk-through skill, at a depth that fits: for one shot on real work, its small path (the steps table); for a repeated test or other participants, the full walk. Settle open points with the requirements skill on one topic. The scenario's specifics come from this walk with the person, not from earlier tests.
3. **Safety.** When the subject runs outside an isolated VM or container (a shared machine, production, anything holding others' data or jobs), write down with the person, before any runbook: what it may read, write and start; how much load it may put on others (CPU, disk, memory, network, how long); how a run is stopped; what must never happen; what is cleaned up afterwards; who owns the machine and who agreed. A forwarded port is bound to the local machine only, unless the person decides otherwise. They head the runbook (the decision record's safety row, `${CLAUDE_PLUGIN_ROOT}/references/decision-record.md`). Propose no command for that machine before; afterwards the agent only reads there until the person allows commands, one at a time. Whatever the terminal prints reaches the agent and its transcript as it happens, and the recording keeps it: say so before the run, keep secrets off the screen (or the recording paused while they are typed), and say what to look through before anything is shared. The person may change or waive any of this for their own machine; say once what that risks.
4. **Channels.** Agree how data travels between the person, the agent and the subject: a view of the person's terminal, log files, forwarded ports, shared folders, the project's tracker. For the terminal, `${CLAUDE_PLUGIN_ROOT}/scripts/record.sh` records output and timing as it goes, never keystrokes, into a new private `run-<n>` folder under `FIELD_TEST_DIR`, the run's evidence folder. The runbook sets `FIELD_TEST_DIR` among its variables: the project's `.claude/field-tests/` (check that git ignores it) or, where the agent cannot read that, a folder it can. The recorder runs where the person types, often another machine than the agent's: say how it gets there (a shared folder, a copy), and go through what it does with the person before it runs, like the runbook (output and timing, never keystrokes; where it writes; private to them). Check each channel from where the agent runs with a harmless probe (read a test line from the recording, one request to the port, a listing of the folder) and show the result, before the run starts.
5. **The runbook.** Write it to `design/field-tests/<scenario>-runbook.md` in the project (tracked), in fenced code blocks, never a table: the variables first, then one command per line with a `#` comment saying what it does, so that it reads as raw text and can be copied out as a shell script; small helpers only, readable at a glance. Everything the person is to do is a step in the runbook, the channel probe first; the chat refers to its steps and adds none outside it. Show the runbook in the reply too, its code blocks as in the file with every command and comment, never summed up in prose or as a list of steps: the person reads the reply, not the file; variables exported before the recording carry into the recorded shell. Ask the person to go through it with you before anything runs; adjust them together; never hand over a script as "run this". Multi-line pastes break in some terminals: one line at a time. The runbook is tracked: no secrets in it, and in a public repository no internal host names or accounts unless the person agrees. `record.sh` needs util-linux `script`. Decide with the person which safety limits the participant must know: those their own actions could break go into the brief as rules of the setting; those the setup enforces stay out. A brief for a participant follows `${CLAUDE_PLUGIN_ROOT}/references/field-test-brief.md` and goes to `design/field-tests/<scenario>-brief.md`; the runbook then holds only the setup and the hand-back. When the person is the participant, the brief is a few lines in the runbook.
6. **The run.** It begins with **the start**, once the open questions are settled: the agent says in its own words that the runbook is ready, which step begins and what it waits for ("The runbook is ready. Please start step 1, the recording, and tell me when it's running. I'll look at it after that."); the person starts and says when it runs, and only then does the agent look; a folder missing before that is no fault. The person works as they normally would and notes things as `#` lines at the prompt, in the notes file, or as "note for the debrief". The agent looks at the live view at each runbook step and when asked, not on a timer. It speaks up unasked in three strengths: a deviation it adapts to, mentioned inline ("you ran it twice, so I'll compare both"); a deviation that may compromise the test, said plainly with what it costs; something unsafe, said at once and loudly. The person can always override; the agent never gatekeeps beyond Claude's built-in safety checks.
7. **Evidence.** The person ends the recording; each session of the run is exported into the run's folder (`${CLAUDE_PLUGIN_ROOT}/scripts/transcript.py export <id> --to <run folder>/<id>`), which stays private; `record.sh --pack` makes one archive of it; the person looks through it for anything private before anything leaves.
8. **Process, then act.** Grade the run with one fresh reader agent and `${CLAUDE_PLUGIN_ROOT}/references/field-test-grade.md`, filled in, against the project's requirements; `transcript.py messages <id>` measures the replies' numbering and length. File each finding by its layer, with the person's yes and, for someone else's run, within what the participant agreed: the subject's in the project's tracker (as its tracker setting says); findings about kaizen itself as a drafted issue for github.com/uellue/skills for the person to send; the method's in `design/field-tests/`. When the person corrects a grade, add the case to `design/field-tests/works-as-designed.md` in a sentence of your own; their words stay in the evidence folder. Offer the next run only after the findings were acted on, unless the person wants repeats from the same state to sample variation.

## Rules

- The person decides and works; the agent proposes, probes, watches and files.
- Say which layer each finding is about.
- Nothing of the evidence leaves the machine without the person's look and yes.
- At the end, one line into the project's ledger, under `## Skill friction`: what in this skill did not fit. If the file is new, announce it first (playbook, Rules).
