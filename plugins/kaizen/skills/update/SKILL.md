# Update

Text id `9b34b628`: first run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py update 9b34b628` as it stands and pass on what it prints, if anything (it is silent when all is well; if it fails, carry on).

An update must never feel like a regression: whatever the project's people established, chose on purpose or said they liked stays as it is until they confirm a change. The person stays in control of every line that changes; the update proposes, shows and asks.

Use plain words with the person: explain a term of this plugin the first time you use it with them, as `${CLAUDE_PLUGIN_ROOT}/references/words.md` does; keep a message to about fifteen lines, one step or question at a time; number items as bold labels (`- **7**`, never `7.`), one sequence across messages, never restarting while any is open.

## Steps

1. **Where the project stands.** Run `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/version.py --project` and read `${CLAUDE_PLUGIN_ROOT}/references/changelog.md` from the project's version up to the installed one (a block without a version line takes every section; a pre-release such as 0.6.0-dev.1 belongs to its release's section, 0.6.0, so a project at a pre-release reads that section again and skips what it already has). Read the project's instruction file (`CLAUDE.md` or `AGENTS.md`, and files it imports), its ledger if any, and its own records of decisions and requirements, wherever it keeps them. Say in one message what the update covers, which items of the changelog apply here, and that it works on a branch; nothing is written before the person agrees.
2. **What the project chose on purpose.** Before proposing a change, look in those records for the project's earlier choice on the same point (a record deliberately not committed, open questions kept in a document of its own, wording someone said they liked, an adaptation of a standing rule) and name it beside the change. Where the plugin's newer default differs, offer the default and keep the project's way unless the person says otherwise; offer to note each kept choice in the instruction file ("Kept on purpose: …"), so that the skills read it next time instead of proposing the default again.
3. **The standing instructions.** Compare the project's copy with `${CLAUDE_PLUGIN_ROOT}/references/standing-instructions.md` line by line, by content: list each line that is new, changed or gone, one numbered item each, in a few words, over two messages when one would run long; list the project's own adaptations (its commands, documents, dependency list) as kept. Ask which numbers to take; merge them into the project's wording ("merge, don't append"), and put the version line, set to the installed version, first inside whatever section holds the block. A copy in the person's own `~/.claude/CLAUDE.md` is outside the project: name it, and offer the same comparison.
4. **New settings and records.** For each item of the changelog that needs an answer (the issue tracker, the ledger's header lines), ask the question it names, once, without guessing; offer to record the answer where the changelog says. The ledger is the one record the update creates when it is missing, at its end, for the answers to the header questions and its own line on what did not fit, after saying where it goes; other records (feedback entries, a stakeholder record) wait until a skill first needs them. The project's own records stay where they are, and the ledger links to them instead of copying them.
5. **The tracker, first look** (from then on `/kaizen:sync` does this; say so). When the project has an issue tracker, read the open issues and pull requests (for GitHub `gh issue list` and `gh pr list`); name those from others that have waited more than two days for an answer as places where the person's answer is needed, each with what it asks of them in one line; the person follows up with people themselves, so draft a reply only when asked (then in `.claude/drafts/`, kept out of git like `.claude/debriefs/`, split into a part for people and a part for agents); post nothing without the person's yes. Note the date of this first look in the ledger's notes, where the first sync starts. Look at issues closed since the project's version too (with no version or date to go by, ask how far back), for open questions in its records that they made stale. Issues stay in the tracker; only what concerns working with the plugin and the agent gets a ledger row, with the link and one line, and a remark there about working with the agent, liked or not, becomes a feedback entry that cites the issue, never the account.
6. **Hand over.** The changes go on a working branch (a new one when the project is on its default branch), committed with the person's agreement; offer a pull request description from the branch's log and diff that names the plugin version applied ("kaizen <version>"), leaving the summary on top to the person. List what was taken, what was kept and why, and what waits for an answer; show where the person's remarks went.

## Rules

- Never change the instruction file, a record or anything upstream without the person's yes for that item; one yes may take a numbered list.
- Say which layer each finding is about: the plugin, the project, or the work with the agent.
- Ideas dropped on the way and offers left open go into the inbox at once (`${CLAUDE_PLUGIN_ROOT}/references/ledger.md`).
- At the end, one line into the project's ledger: what in this skill did not fit. If the file is new, announce it first (playbook, Rules).
