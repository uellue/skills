# Hallway test 2026-11-05: a new colleague with an SEM project, from the README

**Summary (for people).** A fresh agent played a new colleague who wants an agent to operate a scanning electron microscope, starting from the README with no requirements and no code, with made-up answers and real work abbreviated. The path held: README → playbook → requirements → walkthrough → decision record → hallway test (handed back, nothing built) → debrief, and every skill's version line matched its text. The most serious gap: **hardware safety first appears in the hallway test, at the end**; the requirements questionnaire, the walk-through's measured walk, the playbook's build step and the decision record never raise the instrument (stage collisions, beam damage, venting, who authorises moves), so the tester had to raise it itself. Eight findings, decisions with leans below.

Setup: one Opus sub-agent, plugin 0.4.0 at commit `8480733`, Matt Pocock's skills installed (so the "not installed" path was not tested); allowed reading: the README and whatever it and the skills point to; scratch project only, nothing installed; about 78 k tokens, 2.6 minutes, 19 tool calls. Expectations written at 17:09:31 from the README, first command at 17:09:34. Limitation: the tester invented the safety answer itself, so the run cannot show whether the plugin would have raised hardware risk on its own; it shows that no text asks.

## What held up
- The playbook sent an empty project to stakeholders and requirements without inventing content.
- Requirements rounds: recommended answers that "yes" accepts, markers per item, unknowns and deferrals as answers, facts versus decisions.
- The walk-through refused a persona nobody had confirmed (the facility manager).
- The hallway test handed back to the playbook when nothing was built; its hardware and simulator rule is right once reached.
- The debrief's `git check-ignore` step offered the ignore line; its cost was stated before any reading.
- The version line worked in all five skills (E16).
