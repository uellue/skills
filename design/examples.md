# Acceptance examples

One line each: ID, situation and observable outcome, priority, source. Requirements, walk-throughs, decision records, tests and tester briefs cite the IDs; nobody keeps a copy.

- **E1** (must; requirements S3): when a walk-through is invoked and the stakeholder record has no matching persona, then the skill shows the known personas and asks, offering to add one, before walking.
- **E2** (must; requirements 2.5): when `usage.py` runs on a session, then its output tokens equal the sum over distinct API message ids.
- **E3** (must; requirements S4): when a hallway test ends, then its record exists under `design/hallway/` and names, per defect, what would have caught it.
- **E4** (must; requirements S5, 2.9): when a transcript is exported into a directory git would track, then the export is refused and nothing is written.
- **E5** (must; requirements S5): when a session contains messages the person typed while a turn ran, then the rendering shows them as `USER (queued mid-turn)` and the usage counts them, and harness text is never labelled or counted as the person's.
- **E6** (should; requirements S1): when the requirements interview starts on a topic with an existing record, then its first round is drafted from the record and asks only the frontier questions the record does not settle.

From the walk-throughs of 2026-11-05 (`design/walkthroughs/colleague-first-debrief.md`, `design/walkthroughs/maintainer-check-before-release.md`), run by an agent without a person: simulated; priorities are the agent's proposal. The principal confirmed E7 to E11, E13, E15 and E16 in the requirements round of 2026-11-05; E12 and E14 are still unconfirmed.

- **E7** (should; walk colleague-first-debrief step 3; confirmed by the principal 2026-11-05): when a colleague reads the README only as headings, command blocks and bullets that carry a command (`skim.py README.md`), then the view shows, after the install commands, the command that starts a first debrief.
- **E8** (must; walk colleague-first-debrief steps 4, 5; confirmed by the principal 2026-11-05): when `/kaizen:debrief` is invoked in a fresh session without naming a stretch, then it does not debrief the session it runs in; it shows the project's earlier sessions in a form the person can recognise and says which it will take, or asks.
- **E9** (must; walk colleague-first-debrief step 7; confirmed by the principal 2026-11-05): when the private report's destination would be tracked by git in the person's repository, then the person is told before anything is written, and the coaching is not written where `git add -A` picks it up without their say.
- **E10** (should; walk colleague-first-debrief step 6; confirmed by the principal 2026-11-05): when a debrief would read more than one session, then it states the sessions, their sizes and its expected cost before reading, and waits for the person.
- **E11** (should; walk colleague-first-debrief step 4; confirmed by the principal 2026-11-05): when a bundled script runs on a Python older than it supports, then it stops with one line naming the required version, not a traceback.
- **E12** (must; walk maintainer-check-before-release step 3; unconfirmed): when a skill or reference names a `${CLAUDE_PLUGIN_ROOT}/...` file that does not exist, then `./check.sh` fails and names the file and the path.
- **E13** (should; walk maintainer-check-before-release step 3; confirmed by the principal 2026-11-05): when `./check.sh` runs, then it lists every example in `design/examples.md` that no test or fixture cites.
- **E14** (should; walk maintainer-check-before-release step 4; unconfirmed): when the requirements skill is run against the scripted-principal fixture (testing.md, fixture 3), then the blind grade lists per key item found or not, with the plugin commit and the model, beside the previous run of the same fixture.
- **E15** (should; walk maintainer-check-before-release steps 5, 6; confirmed by the principal 2026-11-05): when a benchmark run is finished, then its result file names the plugin commit, the model, whether the grader was blind, the conditions run and the output tokens, and sits beside the earlier results.
- **E16** (must; walk maintainer-check-before-release step 2; confirmed by the principal 2026-11-05): when the maintainer tries a changed skill by hand in a session, then the session runs the checkout's version and the maintainer can see which version ran.
- **E17** (must; requirements 2.1, language; principal 2026-11-06): when a request uses a word that can be read two ways, or that the project's glossary defines otherwise, then before acting on it the agent says which reading it takes ("I read X as …") and offers to settle the word.
- **E18** (should; requirements 2.1, language; principal 2026-11-06): when a skill makes the agent write to the person (a question, a summary, a document), then a term the person cannot be expected to know is explained or replaced on first use, and one concept keeps one name throughout.
- **E19** (should; requirements 2.1, language and S5; principal 2026-11-06): when a debrief runs over a stretch in which a word was used in two senses, then the report names the word and the moments, and the debrief offers to settle it with the person.
- **E20** (should; requirements 2.1, language and S5; principal 2026-11-06): when a debrief starts on a stretch in which the agent lost track (of the scope, a decision, the level under test), then before writing findings it asks the person what went well, where the friction was and where the agent seemed to lose track.
- **E21** (must; requirements 2.1, language; principal 2026-11-06, from real use of 0.5): when a skill makes the agent send a message with several items, then the items are numbered in one sequence that never restarts within the message, so the person can answer by number.
- **E22** (should; requirements 2.1, language; principal 2026-11-06, from real use of 0.5): when a skill makes the agent send a message, then it is about fifteen lines or fewer as a terminal shows it; what needs more is split into steps, one question or decision at a time.
- **E23** (should; requirements topic field tests and ledger 271, plugin update; agent's lean 2026-11-09, to be reviewed by the principal): when the plugin has been updated and the project's `CLAUDE.md` (or `AGENTS.md`) carries an older copy of the standing instructions, then the agent names the lines that are new or changed since that copy, keeps the project's own adaptations (in devvm: its dependency list, open questions in `spec.md`, its CI commands), and updates only after the person's yes.
- **E24** (should; ledger 271; agent's lean 2026-11-09): when a project's issues live in a tracker and the project's instruction file does not say so, then the agent asks once where they live and how to sync, and offers to record the answer (tracker, repository, the moments to sync, who may post) in that file, which every session reads.
- **E25** (should; ledger 271, 282; principal 2026-11-09): when a project's work lives in an issue tracker, then its issues stay there and the ledger holds only what concerns working with the plugin and the agent: a point of an issue that says something about that gets one ledger row with the link and a one-line summary (in devvm: "agent-written README text unclear to a first user (#16)"), never a copy; the rest of the issue (a bug in the tool) gets no row, and its fix carries `Closes #n`; a linked row is updated when its issue closes upstream.
- **E35** (should; ledger 291; principal 2026-11-09): when the person starts a sync, then the agent reads the tracker setting from the instruction file instead of asking again, reports what fetching and the tracker show (merged, closed, waiting, a branch behind or ahead), marks ledger entries linked to closed issues, names open questions in the project's records that a closed issue made stale, and records the date of the sync in the ledger.
- **E36** (should; ledger 288, 291; principal 2026-11-09): when a sync finds notes in the ledger's inbox, then it proposes one destination for each (an issue, a comment on an issue, a ledger row, dropped, or kept for the debrief) with a draft where something would be posted, and after the person's answer each routed note keeps only its link.
- **E37** (must; ledger 291; principal 2026-11-09, "not exactly on my behalf, but with your support and help"): when a sync finds something that would change a repository or the tracker (a rebase, a push, a post), then the agent shows and explains the command or the draft and runs it only on the person's yes and where they authorised it; otherwise the person runs it with the agent's help.
- **E38** (must; walk-through maintainer-field-test-devvm, step 2; principal 2026-11-09): when a field test of the plugin starts, then its start state is recorded in this repository (the project's commit, the plugin version, a copy of the person's global instruction file), so that a retry begins from the same state.
- **E39** (should; same walk, steps 4 and 6): when the inner role hands back, then the material (the session's transcript, any recording, the notes about the plugin, links to anything posted upstream, the answer to "did we do OK?") reaches this repository without copy and paste, and notes about the plugin are kept apart from the project's own ledger.
- **E40** (must; same walk, step 8; the reset only for kaizen on kaizen): when the maintainer resets for a retry, then nothing of the previous run reaches the next (the noticed file, the agent's memory for the path, drafts and debriefs, the run's VMs, a changed global instruction file), and what was posted or pushed upstream is listed, since it cannot be undone.
- **E41** (should; same walk, steps 3 and 9; principal 2026-11-09): when the maintainer plays the inner role (variant 1), then the brief and the return path are the same a colleague would get (variant 2), so the handovers are tested.
- **E34** (should; ledger 288; principal 2026-11-09): when the person drops an idea or a note during work, then it goes into the ledger's notes as an inbox and is routed at the next tracker sync or debrief: to an issue or pull request ("→ #18"), to a ledger row ("→ row 12"), or dropped; the note keeps only the link, and a note still unrouted after that moment is shown to the person.
- **E26** (must; ledger 271 and the standing instruction on text that leaves the repository; principal 2026-11-09): when a sync or a skill would write to the tracker (a comment, a reply, a label, closing an issue), then it shows a draft split into a part for people and a part for agents and posts nothing without the person's yes; a fix that resolves an issue carries `Closes #n` (or `Refs #n` for a part of it) in its commit or pull request.
- **E27** (should; ledger 271 and 238; agent's lean 2026-11-09): when an issue or pull request from someone other than the maintainer has had no answer for more than two days, then the agent names it and offers a short reply as a draft; remarks with an emotional lean in the tracker become feedback entries that cite the issue number, not the account.
- **E28** (must; requirements topic field tests, rounds 2 to 4; principal 2026-11-09): when the agent prepares a field test, then the participant's brief names the layers (their machine, the tool, what the tool creates, any agent inside), gives the commands for recording and for notes in the moment (with the line zsh needs), lets their own agent turn the recording into a report they see before anything is sent, asks for their "ok" before anything is public, keeps raw recordings out of public trackers, and ends by asking whether we did OK and whether anything in the brief made them uncomfortable.
- **E29** (should; requirements topic field tests, item 22; principal 2026-11-09): when a session involves the plugin, the project under test and what that project creates (a VM, an agent inside it), then each finding says which layer it is about: the plugin, the project, or the field-test method.
- **E30** (should; plugin update; agent's lean 2026-11-09): when the plugin has been updated in a project that predates documents the new version uses (the ledger with its `Public:` and `Message size:` lines, `design/feedback.md`), then the agent says which are missing and creates each when a skill first needs it, after saying where it goes, rather than all at once; the project's own records stay where they are (in devvm: requirements with their source tags, open questions at the end of `spec.md`), and the ledger links to them instead of copying them.
- **E31** (should; plugin update; agent's lean 2026-11-09): when the update changes the project's files (instructions, new records), then the changes go on a working branch with its own pull request whose description names the plugin version it follows, not onto the default branch.
- **E32** (must; requirements topic field tests, round 5, plugin updates; principal 2026-11-09): when an update would change an established workflow or experience of the project (one its records, debriefs, feedback or tracker comments mention, or a choice the project made on purpose), then the agent names it, says what would change, and keeps it as it is until the person confirms; in devvm: the hallway test's report was deliberately not committed (`design/requirements.md`, its source key), the colleague liked the guidance after `./install.sh` (issue 16), and open questions live at the end of `spec.md`.
- **E33** (should; requirements topic field tests, round 5; principal 2026-11-09, the trigger the agent's lean): when the installed plugin is newer than the version a project's records are from (the version line of its standing instructions, or a ledger without the current header lines), then the person is told once per installed version, by the first kaizen skill they run, which command applies the update (built so instead of a session-start hook: the principal chose "the kaizen skills suggest it", ledger 280); the update itself runs as its own skill that only the person starts, and it ends by recording the version it applied.
